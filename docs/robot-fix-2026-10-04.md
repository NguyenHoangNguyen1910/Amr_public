# Robot hardware fixes — 2026-10-04

## Scope and evidence

This change addresses discontinuous filtered odometry and unstable navigation
observed on the Raspberry Pi. It does not assert that wheel calibration, floor
slip, LiDAR timing, or long-term localization accuracy have been validated.
The actual robot still requires supervised motion and navigation tests.

The pre-fix capture showed filtered odometry jumping about 0.278 m between two
messages while wheel odometry and map->odom were unchanged. Navigation defects
were separately reproduced using the installed controller, not inferred from
the appearance of the web map.

## Changes

- Terminal control now has real hysteresis: enter at 0.30 m, leave only beyond
  0.40 m. Position/yaw tolerances, speed limits and collision margins are unchanged.
- A running goal consumes changed SLAM maps, including map growth/origin changes.
  Temporary obstacles retain their expiry in world coordinates. Republishing an
  identical map with a new timestamp does not rebuild the planner. Wrong-frame
  maps are rejected. An invalidated goal stops safely.
- Tracking recognizes measured heading progress, not just translation. Revisiting
  headings by oscillating does not repeatedly reset the watchdog. The watchdog
  timeout is unchanged.
- DWA reuses the exact trajectory already checked for collision when scoring it.
  Sampling, numerical precision and prediction horizon are unchanged. Loop sleep
  subtracts computation time from the configured period rather than adding a full
  period after each computation.
- The action cleanup always publishes stop, including shutdown/error paths.
- Raw-free cells inside obstacle inflation now use the same reachable escape cell
  for scoring as for path construction. Previously both costs were infinite, so
  even safe rotations received negative-infinite progress and lost to STOP.
  Every candidate still goes through unchanged trajectory/scan collision checks.
- Visible LiDAR obstacles keep refreshing their TTL even when the robot's start
  is inflated. Previously scans were dropped in that state: the obstacle expired
  after two seconds, allowed a movement pulse, then reappeared on the next scan.
- EKF pose transformations use the message timestamp in nanoseconds. The previous
  code used seconds in place of nanoseconds and repeated the seconds field when
  constructing a TF timestamp.
- Wheel odometry contributes body-frame vx/vy only. Its integrated pose is in
  `odom_frame`, which has no transform to the EKF's `odom`; no artificial identity
  transform is added. Wheel yaw rate is not fused against the disagreeing gyro.
- IMU contributes gyro yaw rate only. The complementary filter has no magnetic
  heading, so its integrated yaw is not treated as an independent absolute yaw
  observation from the same sensor.
- `imu_covariance_adapter.py` passes through measurements and timestamps at the
  original frequency. Only all-zero (unknown) orientation/angular covariances get
  explicit defaults; known covariances and the unavailable (-1) sentinel survive.
  Standard-deviation defaults (0.10 rad orientation, 0.02 rad/s angular velocity)
  are engineering starting values, **not a measured sensor calibration**. The
  current EKF uses only angular velocity. Its input is `/imu/data_cov`.
- Twist outlier gates remain enabled, at Mahalanobis distance 8 instead of 1.542.
  The old low gate rejected normal start/stop observations in reconstructed replay.
  An injected 5 m/s wheel observation remains rejected with the new configuration.
- `shell.sh` now sources the workspace after the image's interactive `.bashrc`,
  avoiding accidental selection of the old `/root/yahboomcar_ws` EKF.

### Fifth supervised attempt and final-yaw follow-up

After renewed explicit confirmation of a clear route and readiness to Stop, the
single requested goal (2.60, -0.58, 0) was sent. Recording `pi_fixed_nav_05.json`
ended ABORTED about 0.221 m from the goal, at yaw about 2.64 degrees. This was not
successful arrival. Its precise abort reason was not recorded by the old core.

The user's final-heading requirement is correct: successful Navigation requires
both goal position and the red arrow's yaw. A later passive capture
`yaw_fix_shadow_20261004.json` reproduced a blocked shadow session near another
goal; replay eventually found GOAL_BLOCKED. This does not establish the cause of
every hardware attempt, and no new hardware goal was sent in this follow-up.

A deterministic regression reproduced switching from final yaw back to goal
bearing when the estimated distance moves from 0.059 m to 0.061 m. The fix keeps
the final-yaw target through transient position excursions. Position recovery
requires `stable_goal_cycles` consecutive outside samples (8 hardware cycles),
or occurs immediately for displacement beyond terminal entry distance. This is
not a relaxation of completion criteria: success still requires <=0.06 m,
<=0.08 rad, measured low velocity, and consecutive safe stable cycles. The latch
resets on a new goal or leaving terminal control. Collision checks are unchanged.

Planning/sensor errors now reset the stability counter. BLOCKED action endings
log the cause, phase, remaining distance, yaw error, goal and measured pose, rather
than silently aborting with an empty action result. The public action is unchanged.

Validation: 26 local core tests; 41 full ROS tests in an isolated Docker network;
6 isolated ROS end-to-end cases (arrival followed by 180-degree final alignment,
zero/positive/negative final headings, wrapping across +/-pi, and cancellation).
All passed. End-to-end yaw errors were 0.043-0.073 rad, within 0.08 rad. Physical
final-heading completion after this change is **not yet verified**.

After the user confirmed Cancel/stop, only the Navigation process was replaced;
SLAM/EKF/map were preserved and output remained zero. Local source, Pi source and
installed Python runtime hashes match. Backup before this deployment:

## Deployment and operation

Only reviewed source files were copied to `~/quangnv/robot_nav` on the Pi. The
previous source, install tree and shell script were backed up in:

`~/quangnv/robot_nav/.codex-fix-20261004/before.tar`

The first incremental build skipped changes because the transfer archive had old
file timestamps. The reviewed files were touched and CMake force-configured;
the corrected C++ library and new Python executable were then rebuilt and tested.
Existing saved maps were not overwritten.

Run only **one** `ros2 launch bringup web.launch.py` at a time. Two concurrent
launches publish conflicting odometry, TF and map data. During verification a
second launch appeared; both were stopped and a single session was restarted.

Check manual straight/turn/reverse motion before Navigation, then test a short
goal on known free map cells while ready to stop. Terminal approach remains a
forward-facing controller by design; this change does not promise reverse-only
arrival or exact geometric adherence to every displayed path segment.
